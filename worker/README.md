# Applitrack Worker

The API and the built SPA served by one Cloudflare Worker: Hono + D1 + R2, no
container, no separate frontend service, no CORS.

```
browser ──► applitrack.<domain> (Worker)
              ├── /api/*        → Hono routes
              │     ├── D1      (applications, status history, status-flow view)
              │     ├── R2      (PDF attachments)
              │     └── Clerk   (session token verification)
              └── everything else → assets binding (frontend/dist, SPA fallback)
```

Static assets are unmetered; the API fits comfortably in the Workers Free plan
for personal use (100k requests/day, 10 ms CPU per request, 100k D1 rows written
per day, 5 GB storage).

## Layout

| Path | Purpose |
| --- | --- |
| `src/index.ts` | Router: public routes, auth middleware, SPA fallback |
| `src/auth.ts` | Clerk `authenticateRequest()` → user id (test-mode bypass) |
| `src/routes/` | `applications`, `dashboard`, `status-flow`, `downloads` |
| `src/services/trends.ts` | Period windows, trend maths, aggregate query |
| `src/services/attachments.ts` | R2 keys, filename sanitising, signed URLs |
| `src/lib/status.ts` | Status transition rules (ported verbatim from FastAPI) |
| `migrations/0001_init.sql` | Tables, indexes and the `application_status_flow` view |
| `test/` | Vitest suite running inside workerd against local D1 + R2 |
| `scripts/export-sqlite.py` | Convert the FastAPI SQLite file into D1 import SQL |
| `bindings.d.ts` | Secret / test-only bindings not declared in wrangler.jsonc |
| `worker-configuration.d.ts` | Generated by `npm run types` — do not edit |

## Local development

```sh
npm install                       # from the repo root (workspaces)
cd frontend && npm run build      # produces frontend/dist for the assets binding
cd ../worker
npx wrangler d1 migrations apply applitrack --local
npm run dev                       # http://localhost:8787
```

`npm run dev` serves the built SPA and the API. To iterate on the frontend with
HMR, run `npm run dev` in `frontend/` too (port 3000); its Vite proxy forwards
`/api` to `localhost:8787`.

Without Clerk keys the API rejects every request. For local work, put this in
`worker/.dev.vars` (gitignored) and use `Authorization: Bearer user-a-token`:

```
CLERK_TEST_MODE=1
ATTACHMENT_SIGNING_KEY=local-dev-signing-key
APP_ORIGIN=http://localhost:3000
```

## Tests

```sh
npm test          # vitest, runs inside workerd with local D1 and R2
npm run typecheck
```

73 tests cover the ported pytest suite (auth, CRUD, transition rules, user
isolation, status-flow aggregation, trend maths, history bookkeeping) plus the
attachment round-trip through R2 and the signed download URL.

## Database

Migrations live in `migrations/` and are applied with wrangler:

```sh
npm run db:migrate:local     # local .wrangler state
npm run db:migrate:remote    # the deployed D1 database
```

### Importing the existing production data

```sh
python3 worker/scripts/export-sqlite.py /path/to/applitrack.db > /tmp/applitrack-data.sql
cd worker
npx wrangler d1 execute applitrack --remote --file=/tmp/applitrack-data.sql
```

The script keeps primary keys (attachment keys embed the application id), drops
the old trigger and view, and rewrites the naive `"YYYY-MM-DD HH:MM:SS.ffffff"`
datetimes as fixed-width ISO-8601 UTC. Copy the SQLite file off the Dokploy
volume first, and keep the R2 bucket name unchanged so existing
`attachment_key` values still resolve.

## Secrets

```sh
cd worker
npx wrangler secret put CLERK_SECRET_KEY
npx wrangler secret put CLERK_PUBLISHABLE_KEY
npx wrangler secret put CLERK_JWT_KEY          # PEM public key: no Clerk round-trip per request
npx wrangler secret put ATTACHMENT_SIGNING_KEY # any long random string
```

`APP_ORIGIN` (the browser origin Clerk tokens must be issued for) is a plain
variable in `wrangler.jsonc`; set it to the production URL before deploying.

## Deploy checklist

1. `npx wrangler d1 create applitrack` → paste the id into
   `wrangler.jsonc` (`d1_databases[0].database_id`).
2. `npx wrangler r2 bucket create applitrack-attachments` (or point
   `r2_buckets[0].bucket_name` at the bucket that already holds the PDFs).
3. Set `APP_ORIGIN` to the production origin, and the secrets above.
4. `npm run db:migrate:remote`, then import the data if this is a cutover.
5. `cd frontend && npm run build`, then `cd ../worker && npm run deploy`.
6. Add the custom domain to the Worker, then set `VITE_API_URL` unset in the
   frontend build (the default `/api` is correct once both are one origin) and
   update Clerk's authorized parties.

## Deliberate differences from the FastAPI backend

- **No SQL trigger.** `track_status_change` inserted history rows behind the
  API's back, which the status endpoint then had to undo for reset,
  correction and terminal-switch transitions. The Worker writes exactly the
  history rows each transition needs, in the same `db.batch()` as the status
  update, so those cases are atomic and explicit (`test/applications.test.ts`
  pins the resulting rows).
- **Datetimes always carry a zone.** The old API returned
  `"2025-01-15T10:00:00"` (no `Z`), which browsers parse as *local* time. Input
  without a zone is still treated as UTC; output is `...000Z`.
- **Attachments** are stored in R2 via the binding and downloaded through
  `/api/attachments/:id?exp=…&sig=…` (HMAC, 5 minutes) so a new tab needs no
  `Authorization` header. No boto3, no presigning keys.
- **Errors** keep the `{ "detail": "…" }` shape the frontend already reads.
